# 独立窗口 vs 弹层：怎么选

这是模板里最该先读的一页。桌面应用特有的诱惑是"能开一个真窗口看起来很专业"，
所以规则必须写得能当场执行，而不是"视情况而定"。

---

## 缺省规则

> **默认用 dialog。** 只有命中下面 6 条触发条件中任意一条才用独立窗口；
> 一条都不命中就不许用——即使它"看起来更酷"。

记忆口诀：**同屏叠层用 dialog，脱离同屏用 window**；
**用户可能想同时看两张表 → window**。

---

## 升级为 window 的触发条件（任一命中）

| #   | 条件                                                                             | 为什么 dialog 不行                                              |
| --- | -------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| 1   | 需要**并排同时操作**两块内容（对照录入、左右比对、边看列表边填表、跨窗拖拽）     | 遮罩 + 焦点锁定在原页，叠层无法真正并排                         |
| 2   | 需要**独立任务栏条目 / 多显示器 / 拖到副屏 / 单独最小化-置顶**                   | dialog 只是同一渲染进程里的 DOM，永远不可能脱离窗口             |
| 3   | 需要**同一表单并行多开**（同时编辑 3 个对象）                                    | dialog 单例状态互踩，要么堆叠要么被覆盖；window 天生隔离        |
| 4   | **长任务/长会话**，内容存活要跨越主界面路由切换（导出、跑批、上传、监控）        | 切路由 → 组件卸载 → dialog 消失；window 有独立生命周期          |
| 5   | 需要**崩溃/性能隔离**（超大表格/图表重渲染、第三方 HTML、可能 OOM 或白屏的内容） | dialog 崩了整个渲染进程一起白屏；window 是独立 renderer process |
| 6   | 需要**新的渲染上下文**（独立内存、独立 Web Storage、独立滚动与焦点栈）           | 同一 JS 上下文无法隔离                                          |

## 必须留在 dialog 的反向条件（任一命中，别用 window）

| #   | 条件                                                                        | 原因                                                                                              |
| --- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| A   | **强模态短交互**：确认框、必填小表单、单选/多选、日期选择、危险操作二次确认 | Windows 上模态子窗口**不跟随**父窗口（官方文档只在 macOS 提供该行为），多窗焦点成本远高于一个遮罩 |
| B   | 内容不足一屏、打开次数少、结果只在当前页消费                                | 收益低于代价                                                                                      |
| C   | 需要弹层与页面**共享响应式状态且实时联动**（拖动即时更新底表、共享草稿）    | 跨进程实时同步要额外广播，成本立刻上升                                                            |
| D   | 需要**入场/离场动画、精确贴合页面元素**（气泡、定位、抽屉贴边）             | 独立窗口无法与页面 DOM 视觉耦合                                                                   |

## 成本对照（实测数字）

以下两组数字来自本模板的实际埋点，测量方法是主进程在 `did-finish-load` 时
对比 `app.getAppMetrics()` 中 `type === 'Tab'` 的 `workingSetSize` 求和差值。

| 维度                   | dialog                 | window                                                            | 实测说明                              |
| ---------------------- | ---------------------- | ----------------------------------------------------------------- | ------------------------------------- |
| 首屏可交互延迟         | ~0（异步组件几十 ms）  | **174 – 213 ms**                                                  | 5 次采样：174 / 185 / 196 / 204 / 213 |
| 每个窗口的渲染进程占用 | +DOM 节点，可忽略      | **约 150 MB working set**                                         | 见下方"数字怎么读"                    |
| 代码量                 | 1 个组件 + `useDialog` | preset + props/result 契约 + `/w/` 路由 + `WindowGate` ≈ 4 处改动 |                                       |
| 状态同步               | 直接共享 Pinia         | **不共享**，props 进 / result 出                                  | 模板刻意不做跨窗口同步层              |
| 生命周期               | 随页面卸载             | 需处理 X / ESC / 父窗关闭 / 崩溃 与 settle 兜底                   |                                       |
| 崩溃隔离               | 无                     | **有**                                                            | 触发条件 5 的唯一硬收益               |
| 调试                   | 一个 DevTools          | 多窗口多 DevTools                                                 | 多窗口 HMR 已实测可用                 |

### 数字怎么读

`workingSetSize` 是**工作集**，包含与其他进程共享的页，所以 150 MB 这个数**明显高估**了
多开一个窗口的真实私有内存代价（真值通常在几十 MB 量级）。
这里保留高估值的原因只有一个：**结论方向不变**——多开窗口不是免费的，
"因为好看而多开"永远不划算。要拿准确的私有占用，得用任务管理器的"专用工作集"列或
`Get-Process` 的 `PrivateMemorySize64`，那是排查内存问题时才需要的精度。

首屏延迟 174–213ms 是**肉眼可感**的一次性等待，所以模板给窗口页配了 `WindowGate` 骨架屏，
而不是让页面空着等 IPC 回来。

## 边界案例

**1. 同一个业务表单什么时候该从 dialog 升级成 window**

出现"填表时必须对照底表数据"（触发 1）、"需要并行开 3 个"（触发 3）、
"高度超视口需要独立滚动 + 副屏"（触发 2）时升级。

升级动作只有一步：给这个表单加一条 window preset + 一条 `/w/xxx` 路由，
把 `<UserForm :model @done @cancel>` 原样搬过去。
**因为表单主体组件被约定为不 import 弹层、不感知容器，所以不重写任何业务逻辑。**
模板里 `views/system/components/UserForm.vue` 同时被 `MyDialog`、`MyDrawer`
和独立窗口 `w/UserFormWindow.vue` 三处复用，就是这个约定的现成证据。

**2. 长任务**

批量导出（进度要跨路由存活、用户可能切页继续看）→ window。
"正在导出…"只是当前页的 loading 遮罩 → `ElLoading` 即可。

**3. 不要为了"显得企业级"而做 splash / 多窗口**

启动白闪的正解是主窗口 `show: false` + `ready-to-show` + `backgroundColor`，
不需要额外窗口去遮。splash 本身等于多一个渲染进程 + 一套"什么时候关它"的分支，
是这张表里典型的"不命中任何触发条件却用了 window"。

**4. 列表页行内详情不要用 window。**

---

## 默认档位

`MyDialog`（表单/详情）→ `MyDrawer`（超长内容、侧向参照）→ `MyConfirm`（是/否）
→ window（仅命中触发条件）。

在应用里可直接对照操作：**概览页 → 弹层示例 / 独立窗口示例**，
两个页面用的是同一个表单，可以当场对比打开速度、状态是否共享、以及关掉后拿到什么。
